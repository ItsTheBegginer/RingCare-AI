## 0. Context the agent must know

**Product.** RingCare AI helps a person who cannot be at home review events from a Ring camera and be alerted when something needs checking. Two categories: **caretaking** (an older family member may have fallen or needs help) and **security** (a weapon-like object or a face covering is visible). Ring event -> backend downloads the clip -> vision analysis -> rules-based assessment (priority + evidence-based explanation) -> dashboard + alerts. It supports human review. It does **not** diagnose, guarantee fall or weapon detection, identify who a person is, call emergency services, or confirm emergencies or crimes. **Keep security deliberately small: weapons and masks (plus a short list of other incident labels). No away mode, no known/unknown people, no zones.** An optional, read-only **Amazon Bedrock review agent** (Phase 9) adds an advisory second-opinion review to each flagged event *after* the alert has gone out. It is not a chatbot, is never in the alert path, and can never lower a priority.

**Hackathon.** Build, Ship, Shape: Amazon Developer Hackathon, Ring track. Deadline: **Oct 23, 2026, 12:00 PM PDT** (Oct 24, 12:30 AM IST). Judging: technical implementation, design, impact, idea quality. A working demo matters more than polish.

**Current state (verified by the owner, 7/7 baseline checks passed).** Fetching Ring Playground events works, clips are downloaded, OpenCV analysis and keyframe display work, priority labels work, acknowledge/dismiss work, refresh and re-fetch create no duplicates.
**Built but NOT yet verified on real hardware/accounts:** WebM re-encoding for playback (`make_playable`), ntfy/Telegram phone alerts, browser alerts + alarm, 5-minute reminders, the rules-based assessment, polling, webhook. Treat these as unverified until a phase proves them.

**Stack.**
- Frontend: React + Vite + TypeScript + Tailwind in `src/`. `npm run dev` on :3000, proxies `/api` to :8000. API client `src/services/api.ts`; types `src/types/events.ts`; alerts `src/services/alerts.ts`; banner `src/components/layout/AlertBar.tsx`.
- Backend: Python FastAPI in `backend/app/`: `main.py` (routes under `/api`, SSE `/api/stream`, escalation loop, polling loop), `ring.py` (Ring Partner API client), `pipeline.py` (sync -> clip -> analysis -> store; sample clips; `make_playable`), `vision.py` (OpenCV motion gating + HOG person detector), `assess.py` (assessment; today it still contains an Anthropic SDK path that **must be removed in Phase 4 - the assessment is rules-only; the only LLM use is the optional Phase 9 review agent**), `schema.py` (stored row -> frontend `Event`), `notify.py` (ntfy + Telegram), `db.py` (SQLite), `frames.py` (FrameSource).
- Run backend: `source .venv/bin/activate && cd backend && python -m uvicorn app.main:app --reload --port 8000`

**Ring API facts.** Base `https://api.amazonvision.com`. Playground tokens last ~30 min (`RING_ACCESS_TOKEN`; hot-swap with `POST /api/ring/token`). Endpoints used: `GET /v1/devices`, `GET /v1/devices/{id}/status`, `GET /v1/history/devices/{id}/events`, `POST /v1/devices/{id}/media/video/download` with `{timestamp, duration}` in ms (follows redirects; the pre-signed storage URL must be fetched **without** the Authorization header). Ring media carries a watermark. Tokens never reach the browser. `GET /api/ring/debug` shows raw Ring responses.

**AWS services and what each is for.**

| Service | Role in this app | Not its job |
|---|---|---|
| **Amazon DynamoDB** | System of record: events, assessments, caregiver status (new/acknowledged/dismissed), reminder state, caregiver settings. Survives restarts. Conditional writes make ingestion idempotent. | Video storage; analytics. |
| **Amazon Rekognition** (`DetectLabels` only) | AWS's ready-made model, applied to keyframes: person presence, confidence, bounding boxes. Primary detector; HOG stays as fallback. It is a separate AWS model, **not** OpenCV and not built on it. | Body-pose estimation (none offered). A guaranteed fall verdict: its label list (v3.0) includes `Fallen Person`, but its reliability on Ring footage is unproven, so it is one signal among several. Face APIs (never used). |
| **Amazon SNS** | Primary alert channel: publishes "needs checking" and reminder messages to a topic whose subscribers (email; optionally SMS) are the caregivers. | Deciding *whether* to alert (backend does). Browser alerts (frontend does). |
| **Amazon Bedrock** (optional, Phase 9, via Strands Agents) | Runs the single review agent: reads stored evidence with read-only tools and writes an advisory second-opinion review for flagged events. | Deciding priority, sending, delaying or cancelling alerts, acting on events, chatting with users. |
| **Amazon S3** (optional, Phase 10) | Clip storage when hosted off the laptop. | Required for the demo. |

**Non-negotiable rules for the agent.**
1. Honest wording: "needs review", "Ring reported motion", "person detected", "possible fall", "possible weapon seen", "face covering seen". Never "fall detected", "armed intruder", "burglar" or "emergency confirmed". Keep the disclaimer in alerts.
2. Never hardcode or commit secrets (Ring tokens, AWS keys). Use `backend/.env` (git-ignored) and `.env.example` with empty values. Never log tokens.
3. Never present sample video as real Ring footage. Sample clips are labelled in UI and data (`source = "ring+sample-clip"` / `"simulated"`).
4. No custom-trained models, no multi-agent architecture. Keep OpenCV for motion gating and keyframes. The only LLM use allowed is the single optional Bedrock review agent (Phase 9), which must stay read-only, advisory, off by default and outside the alert path.
5. Keep the frontend `Event` shape stable; if it changes, update `types/events.ts`, `schema.py` and every consumer in the same phase.
6. After each phase: run the backend, run `npm run lint`, run the phase's verification, and report PASS / FAIL / NOT VERIFIED. Never mark something working unless it was actually run.
7. One branch and small commits per phase (`phase-N-name`). Tag `baseline-v1` before Phase 1.
8. No features outside this plan. Ask when something is ambiguous.

## Phase 2 - Amazon DynamoDB persistence
**Goal.** DynamoDB is the system of record; SQLite stays as an offline fallback and for tests.
**Design.**
- `backend/app/storage/`: `base.py` (`EventStore` abstract: `init, insert, get, list_events, has_ring_event, set_status, unacknowledged, mark_alerted, clear` + settings get/put), `sqlite_store.py` (current logic), `dynamodb_store.py`. `STORAGE_BACKEND=dynamodb|sqlite`.
- **Table `RingCareEvents`** (`PAY_PER_REQUEST`). PK `event_id` (S): `ring#<ring_event_id>` or `sim#<uuid>`. Insert uses `ConditionExpression attribute_not_exists(event_id)`; a failed condition means "already stored", not an error. Attributes: `home_id` ("default"), `device_id`, `device_name`, `source`, `created_at`, `event_ts` (N), `clip_file`, `video_status`, `vision` (M), `assessment` (M), `thumbnail` (S, <=60 KB; item limit 400 KB), `status`, `note`, `acted_at`, `actor`, `reminders`, `last_alert_at`, `last_alert_error`.
- **GSI `by-home-time`**: PK `home_id`, SK `event_ts` (newest first with `Query`; never `Scan`). **GSI `by-status-time`**: PK `status`, SK `event_ts` (reminder loop).
- **Table `RingCareSettings`**: PK `home_id`; caregiver settings + notification recipients. `GET/PUT /api/settings`; frontend `api.ts` stops using `mockApi` for settings.
- boto3 rejects floats: write a recursive float<->`Decimal` helper (covers `vision`, `assessment`).
- Status writes use `UpdateItem` with a condition so a late reminder write can never overwrite an acknowledgement.
**Config.** `STORAGE_BACKEND`, `AWS_REGION` (suggest `ap-south-1`), `DDB_EVENTS_TABLE`, `DDB_SETTINGS_TABLE`, optional `DDB_ENDPOINT`. Credentials via AWS CLI profile / standard env vars, never in the repo.
**Provisioning.** `backend/scripts/create_tables.py` (idempotent; creates tables + GSIs; waits for ACTIVE). Least-privilege IAM: `dynamodb:PutItem/GetItem/UpdateItem/DeleteItem/Query` on the two tables and their indexes only.
**Done when.** Tables created; events and statuses persist across a backend restart; fetching the same Ring event twice stores one item; ack/dismiss survives refresh and restart; tests pass on DynamoDB Local or `moto`; `STORAGE_BACKEND=sqlite` still works.

## Phase 3 - Amazon Rekognition person detection
**Goal.** Reliable person presence, confidence and bounding boxes, replacing the weak HOG detector as the primary detector.
**Clarification the agent must respect.** OpenCV is an open-source library that runs inside our backend; Rekognition is a separate AWS service with its own pre-trained models and does not use OpenCV. **OpenCV stays local** for motion gating, keyframe selection, thumbnails and `make_playable`; **Rekognition `DetectLabels` does the person detection** on the keyframes OpenCV picks. No model training anywhere.
**Design.**
- In `vision.py` add `VISION_BACKEND=rekognition|opencv` (default `opencv`; `rekognition` only when AWS credentials work). Keep the existing output keys (`person_detected`, `person_frames_pct`, `wide_posture_frames_pct`, `motion_*`, `bbox`, `keyframes`) so `assess.py` and `schema.py` keep working. Add `detector` (`"rekognition"` or `"hog"`) and `per_frame` (`[{t, person, confidence, box}]`).
- Frames: pick `REKOGNITION_MAX_FRAMES` (default 6) spread evenly across the clip plus the highest-motion frame; resize to <=960 px wide; JPEG bytes (<5 MB). Call `rekognition.detect_labels(Image={"Bytes": ...}, MaxLabels=20, MinConfidence=60)`; read label `Person` -> `Instances[].BoundingBox` (`Left, Top, Width, Height` as image ratios) and `Confidence`.
- **Capture the full label set, not only Person.** Use `MaxLabels=40, MinConfidence=50` and store, per frame, the signal labels found. From the AWS label list (v3.0, verified): **fall/injury signals** `Fallen Person`, `Injury`, `Crawling`, `Kneeling`; **normal-posture signals** `Sitting`, `Standing`, `Walking`, `Sleeping`; **context** `Floor`, `Flooring`, `Ground`, `Bed`, `Couch`, `Bedroom`. `Fallen Person` has no bounding box (only `Person`/`Man`/`Woman` do), so the box still comes from `Person`.
- **Security labels (same call, no extra API).** Also record, per frame, the security signal labels found: **weapons** `Weapon, Gun, Handgun, Firearm, Knife, Dagger, Blade`; **face coverings** `Mask, Gas Mask`; **other incidents** `Fighting, Window - Broken, Fire, Smoke`. All exist in the AWS label list v3.0; whether the image call returns each one is for the spike test to show. `Gun` and `Knife` also have bounding boxes.
- **Spike test first (before wiring anything).** AWS docs say image `DetectLabels` does not support activities, and it is not clear whether `Fallen Person` comes back from the image call or only from video label detection. Run `detect_labels` on 8-10 staged still images (fallen on floor, sitting, standing, lying on a sofa, lying on a bed, bending, exercising on a mat, empty room, a person wearing a ski mask or scarf over the face, a medical mask, a hoodie, a kitchen knife on a counter, a toy gun). Safety: use stock photos or ordinary items only; never point a real weapon, even a fake-looking one, at a person. Tabulate which labels appear and at what confidence. If the image call never returns `Fallen Person`, record that and ask the owner before considering the S3 + `StartLabelDetection` route (video label detection supports activities).
- Compute: person presence per frame; `wide_posture` when `(Width*img_w)/(Height*img_h) > 1.0`; stationary share from box movement between consecutive sampled frames; thumbnail = frame with the highest person confidence; `bbox` percentages from that frame.
- **Do not gate Rekognition on OpenCV motion**: a person lying still is the case that matters most. Cap spend with `REKOGNITION_DAILY_CAP` (default 300 images/day); when exceeded, fall back to HOG and say so.
- **Fallback.** Any failure (no credentials, throttling, access denied, network) -> use HOG for that event, record `detector: "hog (rekognition failed: <ErrorName>)"`. Never crash ingestion.
- **Privacy.** Use `DetectLabels` only. Never call face APIs, never create collections, never store frames in AWS. Document that frames are sent to AWS for analysis and note AWS AI-services data-use settings in the README.
- IAM: `rekognition:DetectLabels` only. Cost: about $0.001/image (check the Rekognition pricing page and the account's free-tier status).
**Done when.** The spike-test table exists (which signal labels the image API returns, with confidences, including false positives such as sofa/bed/exercise); on the staged clips (walking, sitting, lying still, empty room, staged fall) Rekognition output is shown next to HOG output in a table (put it in the README, including misses); fallback works when credentials are removed; unit tests use a stubbed client with canned `DetectLabels` responses.

## Phase 4 - Evidence-based assessment
**Goal.** A caregiver understands why an event got its priority and what to do.
**Build.** (1) Standard format stored as a map and rendered in the modal and alerts: `summary`, `observed_evidence[]` (concrete: "person in 4 of 6 frames", "little movement for ~14 s"), `priority`, `confidence` + `limitations[]` ("watermarked video", "single-frame detector", "10 s clip"), `recommended_action`, `engine`, `detector`, `analysis_version`. (2) **Rules only - no LLM in the assessment or alert path** (the optional Phase 9 agent is separate and advisory). Remove the Anthropic SDK code, the `anthropic` dependency and `ANTHROPIC_API_KEY`. `assess.py` is deterministic: it builds the standard format from detector signals using thresholds kept in config, and every explanation sentence is generated from templates filled with the actual evidence (labels, confidences, frame counts, durations) - never invented text. `engine` is always `"rules"`. Validate the stored assessment against the standard format (invalid -> safe default, never a crash). Include Ring metadata, detector name and the detector numbers in the evidence list. (3) Wording distinguishes *Ring motion event* vs *person detected* vs *low/horizontal-posture hint*; never a verified fall. (4) Analysis failure -> priority low, "No video could be analysed - please check manually". (5) An event is assessed once; re-fetching never creates a second or contradictory assessment (guaranteed by Phase 2 conditional insert). (6) Extend `schema.py` -> `aiAssessment` (`evidence`, `limitations`) and the modal.
**Possible-fall indicator (the central feature, experimental).** Add `fall_indicator` to the assessment: `{level: none|possible|likely, signals: [...], missed_signals: [...]}`, built only from verified inputs: (a) Rekognition `Fallen Person` / `Injury` / `Crawling` confidence across frames, (b) geometry: the person's box turns from tall to wide during the clip, (c) the person then stays still for >= `FALL_STILL_SECONDS` (default 5), (d) context: `Floor`/`Ground` present and `Bed`/`Couch`/`Sleeping` absent raises the level, those present lower it, (e) there is **no model cross-check**, so compensate with stricter thresholds and require several signals together. Rules: `possible` needs (b)+(c) or a strong (a); `likely` needs (a)+(b)+(c) with floor context. A `possible`/`likely` level sets priority high and the alert text reads "Possible fall - please check now" - never "fall detected". Optional stretch if time remains: a free local pose model (e.g. MediaPipe Pose) as an extra head/hip-height signal. State the limits in the UI: 10 s window, watermark, camera angle, falls out of view are invisible.
**Security indicator (weapons and masks only - keep it simple).** Add `security_indicator` to the assessment: `{level: none|possible, signals: [{label, confidence, frame_t}], notes}` and an event `category` (`caretaking`, `security`, or `both`). Labels come from the same Rekognition call. Keep the label lists configurable (`SECURITY_WEAPON_LABELS`, `SECURITY_MASK_LABELS`, `SECURITY_OTHER_LABELS`); do **not** include `Hood`/`Hoodie` (too common) and drop any other-incident label that the spike test shows is never returned. To limit false alarms: require confidence >= `SECURITY_MIN_CONFIDENCE` (default 80) in >= 2 sampled frames, or >= 90 in a single frame; a `Knife` with kitchen context (`Kitchen`, `Cooking`, `Food`) is downgraded; a face covering counts only when a `Person` is present in that frame. There is no model cross-check, so show the raw labels, confidences and frame times as evidence and let the caregiver judge. Priority: weapon -> high; face covering -> medium; both -> high. Wording: "Possible weapon seen" / "Face covering seen". Unit tests: weapon label in 1 vs 2+ frames, kitchen knife, mask without a person, medical-mask control.
**Done when.** Every event shows evidence, limitations, priority and action; tests cover: no motion, motion without person, person moving, person still, wide posture, analysis error.

## Phase 5 - Amazon SNS notifications + five-minute reminders
**Goal.** Reliable AWS alerts when an event needs checking, with escalation if nobody responds.
**Design.**
- `notify.py` -> `Notifier.send(event, reminder_n)` with `SnsNotifier` (primary), `NtfyNotifier`, `TelegramNotifier`; `NOTIFY_CHANNELS=sns,ntfy`. Browser notification + alarm stay in the frontend.
- **SNS.** Topic `ringcare-alerts` (`SNS_TOPIC_ARN`). `Publish` with a category-specific Subject (caretaking: "RingCare: please check on <name>"; possible fall: "RingCare: possible fall - check now"; security: "RingCare: possible weapon or face covering seen - check now") and body: camera, summary, evidence, recommended action, dashboard link, and *"This is a review prompt, not a confirmed emergency. If you think someone is in danger, call them or emergency services."* For security alerts add: *"Do not confront anyone. Call local emergency services if you believe there is a real threat."* `MessageAttributes: {severity}`.
- **Subscribers.** Email is the reliable default (recipient must click the confirmation link). SMS via SNS is best-effort and **may not work for India** (sender registration requirements; new accounts start in the SMS sandbox limited to verified numbers). Document this; do not block the project on SMS.
- **Policy.** Alert when priority >= `NOTIFY_MIN_PRIORITY` (default medium). Reminders every `ESCALATE_AFTER_MIN` (default 5), up to `MAX_REMINDERS` (default 3), while status is not acknowledged/dismissed; acknowledge or dismiss stops them. The loop reads `by-status-time`; each send is recorded with a conditional `UpdateItem` (`reminders = :expected`) so duplicates cannot happen, even after a restart.
- Failures: catch, retry with backoff (max 3), log without secrets, store `last_alert_error`, never break ingestion.
- **Alerts never wait on anything else.** The optional Phase 9 review agent runs only after an alert has been sent and can never delay, cancel or downgrade one.
- Endpoints: `POST /api/notify/test` (per-channel result), `GET /api/notify/config`. `backend/scripts/create_topic.py` creates the topic, subscribes an email, prints the ARN. IAM: `sns:Publish` on that topic only.
**Done when.** Test email arrives through SNS; a medium/high event sends one alert; an untouched event sends reminder 1 at ~5:00-5:30 (loop runs every 30 s); acknowledging at 3 min cancels it; dismissing cancels it; an SNS failure is logged and the app keeps running; no duplicates after a restart. Test timing with `ESCALATE_AFTER_MIN=1`, then restore the default. Browser notification and phone (ntfy) verified separately; document anything blocked.

## Phase 9 - Optional: Amazon Bedrock review agent (only if Phases 1-8 are verified; hard stop Oct 21, 12:00 IST)
**Goal.** One AI agent (an Amazon Bedrock model driven by Strands Agents) that **reviews each flagged event** and writes a structured second opinion. It is **not a chatbot**: nobody talks to it, it takes no free-text input from users, and its output is a fixed-format record stored with the event.
**What it does.** For an event with priority >= medium (or a fall/security indicator >= possible), *after the alert has been sent*, the agent uses tools to read the evidence, compare it with recent events from the same camera, optionally look at the keyframes, and return `agent_review`.
**Tools (read-only, whitelisted; no write tools exist).** `get_event_evidence(event_id)`: stored labels, confidences, per-frame data, rule outputs, Ring metadata. `get_recent_events(camera_id, minutes)`: summaries of recent events (e.g. "third motion event in 10 minutes"). `get_keyframes(event_id)`: up to 4 stored JPEG keyframes, only if the chosen model accepts images.
**Output (validated JSON, stored as an `agent_review` map on the event).** `agrees_with_rules` (agrees | disagrees | uncertain); `observations[]` (each cites the evidence field or label it relies on); `possible_false_positive_reasons[]` (e.g. kitchen knife in a cooking scene, medical mask); `suggested_action`; `suggested_priority` (never below the rules' priority); `confidence`; `model_id`; `status` (ok | unavailable | invalid | skipped_cap); `created_at`. Observations without cited evidence are dropped; anything unsupported is marked uncertain.
**Safety invariants (enforce in code and test; do not rely on the prompt).**
1. Rules decide priority and alerts. The agent can only add a visible note such as "agent suggests higher concern". It never changes `priority`, never cancels, delays or downgrades an alert, and never triggers extra alerts.
2. Read-only: no tool can acknowledge, dismiss, delete, notify, call anyone, or write anything except storing its own `agent_review`.
3. Runs after the alert is sent, as a background task, with timeout `AGENT_TIMEOUT_S` (default 30). Any failure (no model access, throttling, invalid output) -> `status: unavailable|invalid`; the event is unaffected.
4. A `suggested_priority` below the rules' priority is clamped to the rules' priority and logged.
5. Off by default (`AGENT_ENABLED=false`). With it off the app behaves exactly as before.
**Config and AWS.** `AGENT_ENABLED`, `BEDROCK_REGION`, `BEDROCK_MODEL_ID` (read from env, never hard-coded; check which vision-capable model the owner can use in that region and enable model access in the Bedrock console), `AGENT_TIMEOUT_S`, `AGENT_DAILY_CAP` (default 50 reviews/day; beyond it skip with `skipped_cap`). Dependencies: Strands Agents SDK + boto3 (confirm the current package name and API in the official docs before coding). IAM: `bedrock:InvokeModel` (and the streaming variant only if used) on that model's ARN only. DynamoDB is schemaless: add the `agent_review` attribute, no table change. `/api/health` reports `agent: enabled|disabled`.
**Privacy and cost.** Evidence and keyframes are sent to Bedrock: say so in the README and check AWS's data-handling terms for the chosen model. Each review costs a small amount per call; the daily cap bounds it.
**Frontend.** In the event modal, a clearly labelled **"Second-opinion review (AI, advisory)"** panel: agreement, observations with their evidence, false-positive reasons, suggested action; states for pending and unavailable. It is never styled as the official priority.
**Tests.** Stub the Bedrock/Strands client. Cover: an attempt to lower priority is clamped; the tool list contains only the three read-only tools; timeout and invalid JSON are handled; failure leaves the event untouched; `AGENT_ENABLED=false` skips everything; the daily cap skips.
**Evaluation (README table).** Run the agent on the staged fall, security and control clips and record agrees / disagrees / uncertain against ground truth, where it was wrong, and where its false-positive notes helped. Do not claim more than the table shows.
**Done when.** With the flag on, flagged events get a stored, validated review that appears on the card after the alert has already been delivered; every invariant test passes; the app still works with the flag off; the evaluation table exists. If any of this is untrue at the hard stop, ship with the flag off and remove the agent from the README and description.
